# Phase 2 — Dataset Discovery Notes

**Phase:** 2 — Dataset Discovery and Profiling  
**Date:** 2026-08-31  
**Author:** CloudShield IQ Project  
**Status:** Complete

---

## Objective

Identify, evaluate, and select datasets suitable for training the ML anomaly detection
and risk classification models in CloudShield IQ (Phases 5–6). Document selection
rationale, rejected candidates, and key implications for downstream phases.

---

## Dataset Candidates Considered

### Candidate 1: KDD Cup 1999 / NSL-KDD

| Attribute | Detail |
|---|---|
| Source | UCI Machine Learning Repository |
| Rows | ~5M (KDD99), ~125K (NSL-KDD) |
| Features | 41 network features |
| Labels | Normal, DoS, Probe, R2L, U2R |

**Decision: Rejected**

> [!WARNING]
> KDD99 and NSL-KDD are widely considered outdated for current research. Major criticisms:
> - Traffic generated in 1998 — does not reflect modern cloud network patterns
> - Widely reported to have ~80% redundant records in training set
> - NSL-KDD improves on this but still reflects pre-cloud infrastructure
> - Many features are network-protocol-level (TCP flags, packet counts) that don't map to cloud audit log fields
>
> Using KDD99/NSL-KDD in a 2025 final-year project would be academically weak.

### Candidate 2: UNSW-NB15 Network Intrusion Dataset

| Attribute | Detail |
|---|---|
| Source | UNSW Canberra Cyber (2015) |
| Rows | ~257,000 |
| Features | 49 engineered + 1 label |
| Classes | Normal + 9 attack categories |
| License | Free for research, citation required |

**Decision: Accepted as supplementary dataset (Phase 5+)**

**Rationale:**
- Post-2015 — more relevant than KDD99 derivatives
- Widely cited in academic network security ML literature (>1,500 citations)
- Realistic class distribution (not artificially balanced)
- Published feature semantics — can audit feature engineering decisions
- Suitable for demonstrating anomaly detection methodology
- Does NOT require registration or payment

**Limitation for CloudShield IQ:**  
UNSW-NB15 captures network-layer features (flow duration, packet bytes, TCP flags),
not cloud control-plane events (IAM role changes, S3 bucket policy modifications).
It can demonstrate the ML methodology but cannot directly substitute for cloud audit
log data.

**Plan:** Download in Phase 5 when the ML pipeline is being built. Use for:
1. Baseline model benchmarking (compare against published UNSW-NB15 results)
2. Technique validation (anomaly detection pipeline testing)
3. Academic citation in the project report

**Citation:**  
Moustafa, N. & Slay, J. (2015). UNSW-NB15: a comprehensive data set for network
intrusion detection systems. *MILCOM 2015 — 2015 IEEE Military Communications Conference*.
DOI: 10.1109/MILCOM.2015.7357535

### Candidate 3: CIC-IDS-2017 / CIC-IDS-2018

| Attribute | Detail |
|---|---|
| Source | University of New Brunswick, Canadian Institute for Cybersecurity |
| Rows | ~2.8M (2017) / ~16M (2018) |
| Features | ~80 flow-level features |
| Classes | Benign + 14 attack types (2018) |
| License | Free for research |

**Decision: Deferred — not needed for Phase 2 scope**

**Rationale:** Very large (16M rows in 2018 version) — impractical for a final-year
project with limited compute. Consider sampling a 50K–100K subset in Phase 5 if
the UNSW-NB15 baseline proves insufficient.

---

### Candidate 4: Kaggle Cloud Security Datasets

Multiple Kaggle datasets were reviewed:

| Dataset | Verdict |
|---|---|
| "Cloud Security Misconfigurations" | Inconsistent provenance — not clearly documented |
| "AWS Security Events" | Small (<5K rows), questionable labelling |
| "Azure Activity Log Anomalies" | Proprietary format, poor documentation |

**Decision: Rejected** — None had sufficiently documented provenance, schema definitions,
or licences suitable for an academic project where all data decisions must be justified.

### Candidate 5: Synthetic Cloud Security Events (Generated)

| Attribute | Detail |
|---|---|
| Source | Generated by `ml/scripts/generate_synthetic_data.py` |
| Rows | 8,000 |
| Features | 15 (see column list below) |
| Anomaly rate | 5% (400 anomaly events) |
| Seed | 42 (fully reproducible) |
| License | Project-internal — no restrictions |

**Decision: Accepted as primary dataset for Phases 2–4**

**Rationale:**
- Directly models cloud control-plane events (CloudTrail / Activity Log structure)
- Fully documented field semantics (defined in generator script)
- Reproducible from a fixed seed — academically traceable
- Anomaly rate (5%) calibrated to realistic cloud security incident base rates
  (Verizon DBIR 2024: median time-to-detect is days, implying low day-to-day anomaly %)
- Schema aligns with the CloudShield IQ common data schema (Phase 3)
- Allows development of the full ML pipeline without gating on external data access

**Limitation:**  
Synthetic data cannot capture real adversarial behaviour patterns. Models trained only
on synthetic data will have unknown real-world performance. The UNSW-NB15 supplementary
dataset and future live AWS CloudTrail integration (Phase 13) will address this.

## Key Observations for Phase 3 (Common Schema)

1. **Cloud provider field is essential** — all events must be tagged with `cloud_provider`
   (aws/azure/gcp) to support multi-cloud aggregation.

2. **Action field requires normalisation** — AWS, Azure, and GCP use different action
   naming conventions (e.g., `RunInstances` vs `Microsoft.Compute/virtualMachines/write`
   vs `compute.instances.insert`). The common schema must map these to a canonical
   action namespace.

3. **Session duration is sparse** — 40.4% of events have no session duration
   (API calls made by service accounts). The schema must allow null session fields.

4. **Risk score should be derived, not stored** — the `risk_score` in the synthetic dataset
   is a label for training targets. In production, the ML model outputs the score; it
   should not be stored as a raw input feature.

5. **Anomaly label is binary** — Phase 5 (unsupervised anomaly detection) will produce
   a continuous anomaly score; Phase 6 (supervised classification) will use the binary
   label. Both representations need to be supported in the schema.

6. **Timestamp standardisation** — all timestamps should be stored in UTC ISO 8601
   format. The synthetic dataset already uses this convention.
